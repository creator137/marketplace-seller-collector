# Codex implementation prompt — marketplace-seller-collector

> **Инструкция для Codex:** прочитай этот файл целиком и сразу приступай к реализации проекта. Не останавливайся после составления плана. Работай автономно, проверяй результат командами и тестами, не перекладывай рутинные шаги на пользователя.

## 0. Главная цель

Нужно быстро собрать рабочий законченный MVP веб-сервиса **marketplace-seller-collector** для сбора базы продавцов маркетплейсов.

Это небольшой коммерческий проект. Главный принцип: **максимально использовать готовые open-source решения, стандартные возможности фреймворка и лёгкие готовые UI-компоненты; не писать с нуля то, что уже существует; не переусложнять архитектуру**.

Нужно экономно расходовать время и контекст Codex: меньше длинных архитектурных рассуждений, больше коротких проверяемых итераций.

## 2. Что должен делать продукт

Пользователь через веб-интерфейс выбирает:

- маркетплейс;
- один или несколько городов;
- одну или несколько категорий;

и запускает сбор данных в фоне.

На старте поддержать:

- **Ozon**;
- **Wildberries**;
- **Яндекс.Маркет**.

Начальные города:

- Уфа;
- Челябинск;
- Екатеринбург.

Список городов должен расширяться через БД/админку без изменения кода.

Сервис должен:

- находить продавцов;
- сохранять их в БД;
- не создавать дубли при повторном запуске;
- отображать прогресс фоновой задачи;
- показывать результаты в таблице;
- хранить историю запусков;
- экспортировать результат в `.xlsx`;
- дополнительно обогащать продавца **только через DaData по ИНН**.

## 4. Данные продавца

Единая модель продавца должна поддерживать следующие поля, когда источник их реально отдаёт:

- marketplace;
- external_seller_id;
- seller_url;
- название продавца;
- категории;
- ИНН;
- мобильные телефоны;
- городские телефоны;
- email;
- сайт;
- Telegram-ссылка, технически сформированная из мобильного номера;

## 5. DaData

Использовать официальный DaData API.

Секрет:

```env
DADATA_TOKEN=
```

Если у продавца найден ИНН:

1. выполнить запрос в DaData;
2. дополнить только реально доступные данные из ответа;
3. в первую очередь интересуют:
   - название;
   - юридический адрес;
   - телефоны;
   - email;
   - сайт;
   - реквизиты, которые уже предусмотрены моделью;
4. данные marketplace не уничтожать;
5. контакты объединять и дедуплицировать;
6. сохранять источник данных.

Если DaData ничего не вернула — это нормальный результат, задача не должна падать.

**DaData — единственный внешний enrichment-источник.**

## 8. Anti-bot и HTTP стратегия

Приоритет реализации:

1. публичные/internal JSON HTTP endpoint'ы;
2. `curl_cffi` или обычный HTTP client;
3. необходимые cookies и browser-like headers;
4. разумный rate limit;
5. retries + exponential backoff;
6. изоляция transient errors.

**Не начинать с Selenium/Playwright.**

Playwright допустим только как локальный fallback конкретного адаптера, если live smoke-test показывает, что HTTP-вариант сейчас реально не работает.

Не реализовывать в MVP:

- browser farm;
- сложную proxy rotation систему;
- CAPTCHA solver;
- большой stealth framework;
- распределённый scraping cluster.

Если marketplace требует cookies, хранить их через env/config и не коммитить реальные cookies в git.

## 10. Marketplace adapters

Сделать небольшой общий интерфейс, без избыточной абстракции.

Пример:

```python
class MarketplaceAdapter:
    def get_categories(self): ...
    def discover_sellers(self, category, **kwargs): ...
    def fetch_seller(self, ref): ...
```

И реализации:

- `OzonAdapter`;
- `WildberriesAdapter`;
- `YandexMarketAdapter`.

Можно выбрать async/sync API, которое лучше подходит текущему коду. Главное — единая понятная точка входа.

Каждый адаптер переводит доступные marketplace-данные в общий `SellerData` (`dataclass`, Pydantic model или простой DTO).

Не пытаться заставить все marketplace отдавать одинаковый raw response.

## 11. Дедупликация

Внутри одного marketplace приоритет ключа:

1. `marketplace + external_seller_id`;
2. fallback: `marketplace + normalized seller_url`.

Повторный запуск не создаёт вторую запись продавца.

Если продавец уже существует:

- обновить `last_seen_at`;
- обновить доступные изменившиеся поля;
- объединить контакты;
- не стирать полезные ранее найденные данные пустыми значениями.

Не строить сложный cross-marketplace entity resolution.

Один и тот же ИНН на Ozon и WB может оставаться двумя marketplace seller records. ИНН нужен прежде всего для enrichment/поиска и аналитики.

## 14. Background jobs

Сбор должен выполняться в фоне через RQ.

Сущность `CollectionJob` должна содержать примерно:

- id;
- user;
- marketplace;
- выбранные города;
- выбранные категории;
- status: `queued`, `running`, `completed`, `failed`;
- total (если известен);
- processed;
- found;
- errors_count;
- error_message;
- created_at;
- started_at;
- finished_at.

Правила:

- web request только ставит задачу в очередь;
- worker выполняет сбор;
- регулярно обновляет progress;
- ошибка одного продавца не должна убивать весь job;
- transient HTTP errors retry;
- после падения отдельных элементов можно сохранить их как failed/error и продолжить;
- при возможности повторный запуск не пересобирает без нужды уже свежие данные.

Не строить сложный scheduler, если он не нужен ТЗ.

## 23. Инкрементальность

При повторном сборе:

- известный seller не создаётся заново;
- `last_seen_at` обновляется;
- новые категории/контакты объединяются;
- пустой новый ответ не должен стирать непустое старое значение;
- DaData enrichment можно не повторять слишком часто для одной и той же записи.

Достаточно простого TTL/условия по `last_updated_at` / `last_enriched_at`, без сложного scheduler.

## 24. Что НЕ нужно обещать/реализовывать

Не пытайся технически «гарантировать»:

- 100% продавцов marketplace;
- 100% телефонов/email;

## 26. Definition of Done

Проект можно считать MVP-готовым, когда:

- `docker compose up` поднимает проект;
- миграции применяются;
- можно создать/иметь пользователя и войти;
- открывается форма нового сбора;
- выбирается marketplace;
- выбираются города;
- выбираются категории;
- запуск создаёт background job;
- web process не блокируется сбором;
- job отображает status/progress;
- продавцы сохраняются в БД;
- повторный запуск не создаёт явные дубли;
- найденный ИНН может быть обогащён DaData при наличии токена;
- результаты отображаются в таблице;
- история запусков отображается;
- Excel скачивается;
- стандартные тесты проходят без live-интернета;
- есть отдельный live smoke-test marketplace adapters;
- README содержит только необходимые команды запуска и настройки.
